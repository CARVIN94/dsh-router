# 块轮询(sticky block round-robin)

> 状态:设计定稿 + 已实现。目标:保留 round-robin 的**多账号均衡**,
> 只把轮转的**触发方式**从「每请求」改成「满意才走」,从而大幅降低
> prompt cache miss。
>
> **2026-09-09 后续:round-robin 已升级为前缀亲和**(§8 天花板落地,
> 见文末 §9)。块轮转降级为**回退路径**——亲和拿不到 `messages`
> (算不出指纹)时才走;块统计(`BLOCK_MIN/BLOCK_HIT_RATIO/BLOCK_MAX`)
> 保留,从「驱动轮转」改为「判降权」(§9.3)。

## 1. 问题:每请求轮转把缓存打碎

上游 prompt cache 按 **API key(账号)** 分命名空间。会话前缀是同一段,
被轮转切到 N 个号上,就等于在 N 个互不相干的缓存命名空间里各写一份。

实测(2026-09-09,`usage.json`,codebuddy,`round-robin`,8 个健康号):

| 指标 | 值 |
|---|---|
| 会话 token 命中率 | **71%~75%** |
| `cached` 分布 | **双峰**:非 0 即 ~98%;miss 即 `cached = 0` |
| miss 时 `prompt` | **全量**(约 190k),不是部分失效 |
| 同会话相邻请求间隔 T | **中位 8s**(n=315) |

双峰说明一件事:不是「前缀部分匹配」,而是**这个号手里有没有本会话的缓存**
——全有或全无。所以 miss 的代价是**整段前缀重算**。

### 为什么当前 N=1 是最坏档

8 个号每请求轮转 → 同一号的复用间隔 = `K × T = 8 × 8s = 64s`。
这 64s 是否还在上游缓存 TTL 内,**完全未知**。实测命中 79%(请求数)/ 71%(token)
说明大致踩在 TTL 边缘。

即:现状把命中率**100% 押在了一个未知的外部参数上**。

## 2. 方案:轮转单位 = 块,不是请求

```
pick():
  留守 = 健康 AND 块内计数 < N_max AND (块内计数 < N OR 块内命中率 < M)
  留守 → 返回当前号
  否则 → 游标前进,切下一个号
  故障(rate_limit / quota / session_dead) → 立即切,不等块满(已有)
```

**均衡没变**:块大小有界([N, N_max]) → 长期看各号请求数仍是 1:1。
变的只是轮转的时间尺度:从 8s 拉到 N×64s。

### 保证下限,不依赖 TTL

块内第 2..N 次请求距上次仅 **8s**,8 秒内的缓存**不可能**被驱逐。
所以块内命中率有个**与 TTL 无关**的下限:

| 块内请求数 k | 块内命中下限 |
|---|---|
| 1(现状) | **0%**(全押 TTL) |
| 4 | 75% |
| 8 | 87.5% |
| 16 | 93.75% |

> 这是**下限**。TTL 宽裕时实际更高。

## 2.1 实测结论(2026-09-09,块轮询首日):多会话打架才是主因

上线后两组数据对照:

| 时段 | 场景 | 命中 |
|---|---|---|
| 11:59–12:03 | 3 个会话并行走 `money`(cb-2/cb-5/cb-3 交替) | **3.8%** |
| 12:03 之后 | 只剩 1 会话独占(cb-3 单号) | **82.5%** |

**账号没坏,是并发会话把缓存挤爆了。** prompt cache 是
**per-account × per-conversation** 命名空间;多会话各自 18 万的大前缀,
被块轮询聚到同一号连续服务,在同一账号缓存里互相驱逐 → 轮流全 miss。

这解释了:块轮询在**单会话**下能到 82%(比旧 71% 好),**多会话并发下反而更差**
(3.8%,因为把打架的请求聚到单号密集互踩)。

**根因不是轮询公式,是缺少会话隔离。** 真正的破法是 **per-session 亲和**
(见 §8 天花板),把每个会话绑定到不同账号,让前缀各自有独立缓存空间。
块轮询只能保证单会话内的块，保证不了跨会话的前缀不被别的会话清掉。

## 2.2 参数语义(用户拍板:单账号内 OR)

真实场景是**单对话长跑**(一个会话几千步),不是多会话并发。痛点是:
同一个会话在 8 个号之间跳,每跳一次前缀全重算。亲和解多会话打架,
**解不了单会话换号**。回到块轮询本身。

```
pick():
  留守 = 健康 AND 计数 < N_max AND (计数 < N OR 命中率 < M)   ← OR
  留守 → 返回当前号
  否则 → 游标前进,切下一个号
  故障(rate_limit / quota / session_dead) → 立即切,不等块满(已有)
```

单一账号内部:
- 命中率**爬上去**(>= M,缓存热了)→ 让位,轮到下一个号(均衡)
- 命中率**没上去**(冷启动/短块)→ 留守继续热(不急着跳)
- 轮次**实在太多**(计数 >= N_max)→ 也换(防死守 + 保均衡下限)

参数:
| 参数 | 值 | 依据 |
|---|---|---|
| `M`(BLOCK_HIT_RATIO) | 0.85 | 实测 hit 样本 98~99.7%,85% 是"确实热了"的宽松判据 |
| `N`(BLOCK_MIN) | 16 | 最短驻留,防冷启动误切。块越大越少付块间驱逐,但均衡粒度越粗 |
| `N_max`(BLOCK_MAX) | 48 | 3×N:命中率一直上不去时也要让位,防死守 |

> ⚠️ `N` 的真实成本受 TTL 约束:这块该号空闲期间它守的前缀若被上游
> 驱逐,下轮回来仍是 cold miss。TTL 未知,16 是**保守起步值**,跑一轮
> usage.json 按 uid 下钻看块内命中率再调。

## 3. 换号:命中率达标 / 份额用够,都不是"命中率低"

**换号 = 付费**——下一个号要重算这段前缀。所以换号只能由"这个号已经把
价值榨干"触发:

```
换号 = (计数 >= N OR 命中率 >= M)   OR   计数 >= N_max   OR   故障
       └── 命中达标(热了)或份额用够 ──┘   └─ 兜底 ─┘
```

> 注意:「命中率 >= M 就换」是 OR 语义下的让位规则。**正反馈死锁不复存在**:
> 换号由 `计数>=N` 或 `命中率>=M` 触发,都不是「命中率低」触发的。
> (若误把「命中率低」当切号条件,会切→cold miss→命中率 0%→再切→…锁死 0%,见 §5。)

### 命中率在 OR 语义下的角色

它是**留守条件**、不是切号执行器:
- `命中率 < M` → 留守这个号(继续热),不逃
- `命中率 >= M`(缓存热)→ 放行,让位给下一个号(均衡)
- 冷启动(cold miss)无害:第一个请求命中率 0% → 留守,继续热身

### M 与 N 的取舍(单账号)

`N`(BLOCK_MIN)= 最短驻留,防冷启动误切。热会话命中率很快爬到 M,
所以一个号实际服务约 `min(N, 达到M所需的次数)` 就换:
- N 越小 → 换号越频繁 → 均衡粒度细,但块间驱逐 miss 多
- N 越大 → 一块守得久 → 少付驱逐,但均衡粒度粗、冷号占份额久
| 90% | 10 |
| 95% | 20 |

实测 hit 样本本身 98~99.7%,故 M=85% 是「确实热了」的宽松判据。
**M 与 N 只需定一个**,另一个是它的函数;取 `N = ceil(1/(1-M))`。

## 4. 两个必须补的洞

### 4.1 N_max 绝对兜底(防死锁)

若某号缓存就是热不起来(上游不支持 / 容量被别的会话挤爆),
命中率**永远 < M** → 永远留守 → **整个会话锁死在这一个号上**,均衡归零。

`N_max` 保证无论命中率如何,到点必走。默认 `4 × N`。

### 4.2 留守到 N_max 仍不达标 → 降权

兜底切走后若不处理,下一轮它又会来占一个完整 N_max 块。缓存无效的号
反复拿满额份额,会把均衡拖成「按号均分」而非「按**有效**号均分」。

补:留守 `N_max` 次命中率仍 < M → 标记该号**缓存无效** → 后续轮转跳过。
冷却一段时间后可恢复(上游容量/策略会变,不做永久判决)。

> 这是**账号质量判断**,不是每次请求的路由决策,不进 `pick()` 热路径。

## 5. 参数

| 参数 | 默认 | 说明 |
|---|---|---|
| `N` | 8 | 最小块:达到才考虑切 |
| `M` | 0.85 | 切号门槛:块内命中率 >= 此值才允许因「满意」而切 |
| `N_max` | 32 | 绝对兜底,防死锁 |
| 降权冷却 | 10 min | 判定缓存无效后的跳过时长 |

`N = ceil(1/(1-M))`:M=0.85 → N=7,取 8 留余量。

## 6. 状态与边界

- **块状态按 (supplier, model)** 记**,账号池本来就是这个粒度
  (冷却键同理),不新增维度。
- **失败请求不计入块统计**:失败没产生缓存,计入会污染命中率。
- **冷启动无害**:头两次 miss → 命中率 0%/50% → 反正 < M → 留守,
  而这正是期望行为。噪声只会让你多待,不会让你错切。
- **游标跨会话持久**:`rrCursor` 是实例字段(池随进程存活),新会话
  不会从首号重新开始。否则短会话全压 `poolOrder[0]`,均衡散掉。
- **并发会话共享块**:多会话交错时,块按「(模型) 累计请求数」推进,
  不按单会话。这会让单会话的连续请求被别的会话插队,实际块内命中
  低于理论值——**已知天花板**,根治需 per-session 亲和(见 §8)。

## 7. 可观测性前提

`UsageRecord` **无 `uid` 字段**,当前无法归因「哪个号命中差」,
任何调参都是盲调。已补 `uid` 以按号下钻。

验收指标:`usage.json` 的 `cached/prompt`,按 `uid` 分组。
- 健康:>=95% 且 miss 稀疏(只在冷启动/切号)
- 病态:miss 均匀分布(= 每请求切号)

## 8. 天花板(ponytail)

- **per-session 亲和——真正的根治**。实测已证明主因是并发会话打架
  (多会话大前缀在同一号缓存里互相驱逐,§2.1)。块轮询只治单会话内的块,
  **治不了跨会话驱逐**。需 `ChatRequest` 透传会话标识,或用前缀指纹
  `hash(messages 前缀)` 做一致哈希(闭环在 router 内,不需 DSH 改契约):
  每个会话绑定不同账号,前缀各有独立缓存空间,互不清。块轮询是它的低风险
  前置,二者可叠加(亲和负责选号、块负责驻留)。
- **积分感知换挡**:`credits` 已持久化,可做「积分跌破阈值才换挡」。
  但 `credits` 只存最后一次值不带时间戳,需先确认 `status()` 刷新频率,
  否则触发失真。当前未启用。
- **TTL 仍未知**:87.5% 是保证下限,实际可能更高。要精确 N 需反推 TTL
  (同号相邻请求间隔 vs 命中率拟合驱逐拐点)。

## 9. 前缀亲和(2026-09-09 落地,round-robin 的新语义)

### 9.1 机制

```
pick(round-robin):
  fp = hash(messages 前 2 条: role + content 前 512 字符)   ← src/router/prefix-affinity.ts
  绑定表[model][fp] 存在且该号健康 → 返回它                  ← 亲和:同会话永远同号
  否则 → 游标分一个号 + 记绑定(fp → uid)
  块统计(样本按 (model, uid) 跨驻留累计)只用来判降权,不再驱动轮转
  fp 算不出(无 messages/解析失败)→ 回退块轮转(§2 的旧行为)
```

- **会话标识 = 前缀指纹**:取前 **2** 条(system + 首条用户消息)是刻意的
  ——这两个槽位在会话生命周期里永不变化(新消息只往后追加),指纹从第 1 个
  请求起就稳定。取 3 条会在首条 assistant 回复落进槽位 2 时变一次指纹 →
  会话开局多付一次全量重算。「system + 首条消息逐字相同」的会话,缓存前缀
  本来就相同,共享一个号是收益不是冲突。
- **新会话按游标分发** → 不同会话天然散到不同号,per-account 缓存空间互不
  清(§2.1 的打架根治)。
- **绑定失效即重绑**:绑定的号冷却/降权/被禁 → 会话让位换健康号,并更新绑定。

### 9.2 为什么亲和负责选号、块不再负责轮转

亲和本身已保证驻留(同会话永远粘同号),块轮转若继续驱动换号,会把会话
踢出已热的前缀——两者叠加只会互相拆台。块统计保留的真实价值是**号的缓存
质量判定**:某号累计 `BLOCK_MAX`(48) 次命中率仍 < `M`(0.85) → 判缓存
无效 → 降权 10 分钟(可恢复),亲和与回退路径都跳过它。

样本从「按驻留记」改为「按 (model, uid) 跨驻留累计」:亲和开启后多个会话
各绑各的号交错服务,「驻留」概念只在回退路径存在,按驻留记会漏掉大部分
真实反馈。回退路径换驻留时清一次样本(保持旧块语义:新驻留 = 新观察窗口)。
